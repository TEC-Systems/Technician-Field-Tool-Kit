# TEC Systems Field Toolkit

Windows field toolkit for TEC Systems technicians. The installed app is native C# WinForms on .NET Framework; it does not launch or host PowerShell. It includes Windows and network checks, an IP shifter, IP scanner, feedback, and a technician log. The old PowerShell script remains in the repository for reference but is not installed.

## Install and run

- For a new laptop, download `TEC-Systems-FieldToolkit-Install.zip` or `TEC-Systems-FieldToolkit-Install.7z` from the latest GitHub release. Extract it, run `TEC-Systems-FieldToolkit-Setup.exe`, and click **Install**. The 7z archive is provided when a sharing tool does not accept an EXE attachment; the extracted installer matches the release SHA-256 checksum. Setup installs the native app per user, creates a Start menu shortcut, and can create a desktop shortcut. **Launch after setup** is off by default; select it only if you want the toolkit to open immediately. Portable EXEs in older `releases/` folders are for IT testing only. Technicians do not need PowerShell or a batch file to launch the installed toolkit.
- Double-click the **TEC Systems Field Toolkit** icon. The toolkit runs inside its own EXE process and requests Windows administrator rights when an IP change needs them.
- The original TEC emblem also appears in the Windows notification area, darkened for legibility. Minimize keeps the toolkit on the taskbar like a normal window; clicking X hides it in the tray. Single-click the tray icon to reopen it, or right-click for Open Toolkit, Check Updates, and Exit Toolkit. Only **Exit Toolkit** quits the toolkit. Windows may initially place the tray icon in the hidden-icons menu. Launching the toolkit again in the same Windows session reopens the existing instance instead of adding another tray icon.
- The installed version is shown in the toolkit header.
- The installer is currently unsigned, so Windows SmartScreen may show a warning. TEC Systems IT should sign the installer before broad deployment.

The toolkit follows the Windows app theme on launch and responds to Windows theme changes while running. The header theme button sets a manual light/dark choice; use **Follow Windows Theme** in the tray menu to return to automatic mode.

The **Packet Analyzer** tab opens an existing `.pcap`, `.pcapng`, or `.cap` file and gives a plain-language report. A color-coded priority list puts possible duplicate BACnet device IDs, ARP address conflicts, and BACnet error responses first. Each finding explains the clue and suggests a next check; the full text report includes the same list. The report also includes a transparent capture score, BACnet discovery traffic, general DNS, HTTP, TLS, and TCP clues, and detailed protocol, endpoint, and conversation counts. Reports can be saved as text. This tab requires Wireshark with its TShark command-line component. It does not record packets or require Npcap. Captures and reports stay on the laptop and are not uploaded by the toolkit. The score is a triage aid based only on packets in the file; it does not reproduce Optigo's proprietary score. Inspect the original capture in Wireshark for packet-level detail.

The **Activity Report** button opens a local weekly dashboard with saved RDP site and IP profile totals, newly added RDP sites, foreground usage time, a daily activity chart, a by-tool chart, and recent actions. It can export a text report. Foreground time counts when the toolkit window is active; tray time and older sessions are not counted. It reads the toolkit's local log files; no usage data is sent to TEC Systems or an external service. Older releases did not record every action, so historical counts may be incomplete. A sample-data screenshot is attached to each release as `activity-report-preview.png`.

The toolkit checks GitHub Releases when it opens and every 30 minutes while running. A newer release leaves an **Update Available** button visible and shows a notification-area balloon; clicking the button or notification prompts the technician before downloading; the downloaded installer must match the published SHA-256 checksum before it runs. The **Check Updates** button checks on demand.

## Build and publish

Run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\packaging\Build-Installer.ps1` on Windows to build the native app, icon, installer, ZIP, and 7z archive in `dist`. The build machine needs 7-Zip installed. PowerShell is used only by IT to build the release, not by the installed toolkit. The build runs the native launch/tray self-test and verifies the embedded installer payload and 7z archive.

To publish an update, change `version.txt` and commit the changes to `main`. From any signed-in PC or phone browser, open the repository's **Actions > Build installer > Run workflow**, select `main`, check **Publish release**, and run it. GitHub's Windows runner builds the installer, ZIP, and 7z archive, attaches them with `SHA256SUMS.txt` to the versioned release, and makes them available to **Check Updates**. No technician laptop or IT PC needs to stay on. Pushing a matching version tag also publishes a release. Do not publish until the changes are ready for technicians.

Publishing a release makes it available for download; it does not forcibly replace a running installation. **Check Updates** downloads and verifies the update, closes the toolkit, updates the installed files in place, and reopens it without a separate install step. A manually downloaded Setup EXE asks before stopping a running toolkit and continues after it exits. Setup stops only the installed toolkit process, then verifies it is no longer running before replacing files. Closing the main window only hides the toolkit in the notification area. Saved profiles and logs remain in the per-user data folder during an update.

To uninstall, use **Windows Settings > Apps > Installed apps > TEC Systems Field Toolkit > Uninstall**, or run the downloaded Setup EXE and click **Uninstall**. After confirmation, uninstall closes the running toolkit and removes the installed program, startup entry, shortcuts, and this Windows user's saved profiles, passwords, settings, and logs. The downloaded Setup EXE remains in Downloads until you delete it separately. Older uninstallers kept the data folder; running the current Setup EXE also offers **Uninstall** when an installation folder or other leftover registration remains after an interrupted removal.

The installer enables **Start with Windows** for the current Windows user. At sign-in the toolkit starts quietly in the notification area. Right-click the tray icon and uncheck **Start with Windows** to disable it; future updates preserve this choice. Opening the pinned app or shortcut restores the existing window, including when it was hidden with X. The application and installer include a Windows compatibility manifest.

## Saved data

Technician settings, IP profiles, saved RDP sites, and logs are saved per Windows user under `%LOCALAPPDATA%\TEC Systems\Field Toolkit`. Older BMS flow/link and screenshot files remain there but are no longer shown by this app. They are not stored in this repository or shared automatically between laptops. Back up that folder before replacing a laptop or Windows profile.

## Field diagnostics

- **Windows Troubleshooting** shows Open tools shortcuts in alphabetical order and keeps them visible by wrapping them to fit the available width. **Display Settings** opens Windows display settings to adjust screen resolution. It opens `IPConfig /all` in a Command Prompt that stays open. Saved Remote Desktop sites are managed in the dedicated **RDP** tab. The Windows tools list still includes a shortcut to the standard Remote Desktop client. The old webpage field has been removed from this tab.
- **IP Shifter** hides Bluetooth adapters and lists other connected and disconnected adapters, shows their configured IPv4 addresses when Windows exposes them, and saves named adapter/IP/DNS profiles. Its full-width profile list adjusts column widths when the toolkit is resized. Before applying a static IP, it checks current and saved static IPv4 assignments on all local adapters, including hidden Bluetooth and disconnected adapters. An IP held by another adapter blocks the change and names that adapter; reapplying the selected adapter's own IP shows a warning in the confirmation. This checks local assignments, not every device on the network. Applying a change requires Windows administrator rights and confirmation; the toolkit reads the adapter again afterward and shows an IP assigned successfully message only when the requested IP and subnet mask are verified. A mismatch shows a verification warning. Before changing an adapter, the toolkit saves its previous IPv4, gateway, and DNS settings locally. **Restore Previous IP** restores the last saved settings for that adapter after confirmation, including DHCP when it was enabled. Restore points survive a toolkit restart and are removed after a verified restore. Adapters with multiple static IPv4 addresses, multiple gateways, or more than two custom DNS servers are blocked before the change because those configurations cannot be faithfully restored by this action.
- **IP Scanner** sits next to IP Shifter, selects a connected adapter, and fills its real IPv4 subnet whenever the adapter selection changes. It preserves that selection after an adapter refresh and clears an old range if the new adapter has no usable address. **Refresh** reads current Windows adapter settings without leaving the tab; switching tabs does not run the potentially slow Windows adapter query. Large subnets default to a 254-address slice near the laptop. Technicians can enter any ascending range up to 1,024 addresses. It scans with ICMP and common TCP probes (22, 80, 443, 445, 3389), resolves hostnames through reverse DNS with a NetBIOS fallback, shows local ARP MACs and offline MAC-prefix owners when available, and exports CSV. Click a result column to sort it; click again to reverse the order. IP addresses and ping times sort numerically. A MAC-prefix owner may differ from the device brand. Devices that publish neither reverse DNS nor NetBIOS names will still have blank hostnames; silent hosts and filtered services may be absent.
- **Support bundle** exports the current toolkit log with network snapshots, a system summary and service list, or both into a ZIP. Review the package before sharing because it can contain sensitive machine and network details.
- **Export Summary** in Network Troubleshooting saves a readable text report of current adapters, IP addresses, gateways, DNS servers, the last ten IP Shifter changes, and recent network checks from this toolkit session. It works without a saved site. The support ZIP also includes this summary. Ping runs in a separate Command Prompt, so the report records that it was opened but cannot include its result. Review the report before sharing machine and network details.
- **BMS Tools** currently contains **Launch YABE** and a work-in-progress note. YABE is checked in Program Files; technicians can locate Yabe.exe once if installed elsewhere. Previously saved BMS profiles remain in local settings for future use. Use the dedicated RDP tab for remote desktop connections.
- **Network Troubleshooting** includes a Telnet TCP-port check and a shortcut to the optional Windows Telnet Client. The check only proves a TCP connection can open; it does not verify login. Telnet is unencrypted, so use it only on approved networks.
- **Ping Gateway** in Network Troubleshooting shows the connected adapter and gateway it will use. Select another adapter in that list when needed. If Windows reports no usable gateway, the toolkit explains that instead of trying to ping a placeholder value.

## RDP connection manager

The **RDP** tab sits next to IP Scanner and groups saved sites by folder. Select a site to edit its server/IP, username, domain, password, and resolution, then click **Save Site**. For an IP-based site with a local account, put only the IP in **Server / IP**, the account name in **Username**, and the remote PC name in **Domain**. For example: `192.168.1.200`, `smanashirov`, and `EBISERV`. Qualified usernames saved by version 0.3.26 are split into the Username and Domain fields automatically. **New** clears the editor; **Delete** removes the selected profile after confirmation. Site names must be unique.

Use **Search sites** to filter the tree by site name, folder, or server address. Choose **A–Z** or **Z–A** to sort folders and sites. Select a saved site and click **Add Favorite** to place it in the Favorites group above the folders; click **Remove Favorite** to undo it. Favorites remain in their original folders and are saved with the RDP profiles. The IP Shifter saved profile list also offers A–Z and Z–A sorting.

If a saved IP-based RDP site still asks for a password, select it and click **Password Help**. The report shows the exact `TERMSRV/<IP>` target, account format, Credential Manager status, and local registry values for both saved-credential delegation policies and their deny rules. **Copy for IT** copies the report without a password or encrypted credential. Missing policy entries alone do not prove a policy block; compare with a working site and check the Windows Security error. If Windows says the administrator does not allow saved credentials, an administrator can select **Allow this IP** in Password Help. The toolkit adds only that site's exact `TERMSRV/<IP>` to both allow policies, runs a computer policy refresh, and reports whether the rules remain present. **Undo local rule** removes only rules the toolkit recorded as its own, then refreshes policy. These controls require Windows administrator approval and record the action in `%ProgramData%\TEC Systems\Field Toolkit\rdp-policy.log`. They do not use `TERMSRV/*`, change a domain Group Policy, disable NLA or CredSSP, change server authentication, or pass a password on a command line. If a domain policy replaces the local rules, company IT must change the central policy. Refresh the report after applying or undoing a rule; reconnect and test, then retest after reboot or a domain policy refresh. A remote PC can also require a password at every connection.

If Password Help reports a second **Windows logon** entry for the same IP while the toolkit's **Generic** entry matches, **Clear conflicting login** removes only that other Windows Credential Manager entry for the current user and exact RDP target, after confirmation. Close open Remote Desktop windows and reconnect; the toolkit will register its saved credential again. This action does not remove the site's encrypted password. A policy list entry must use `TERMSRV/<IP>`; entering only the IP does not match the RDP credential target.

If Windows says **Your credentials did not work**, the policy may already be permitting delegation while the remote PC rejects the saved password. A Password Help match only compares Credential Manager with the toolkit profile; it cannot verify the remote account. Enter the password that works in the Windows prompt into the site's **Password** field, keep **Save password for this Windows user** checked, click **Save Site**, then reconnect. If Windows saves a corrected password after a prompt, subsequent **Connect** actions keep that Windows entry instead of overwriting it with an older toolkit password. Explicitly saving a new site password replaces the Windows entry.

Choose full screen, fit to screen (a window sized for the current monitor), or a fixed resolution. **Connect**, or double-click a saved site, opens a separate Windows Remote Desktop window using the current editor settings. Sessions are managed by Windows Remote Desktop rather than embedded inside the toolkit.

Passwords are optional. **Save password for this Windows user** encrypts the password with Windows DPAPI for the current account on this laptop. When a saved site connects, the toolkit also registers its credential in Windows Credential Manager for that server, so Remote Desktop can use it without asking again where server policy allows. Passwords are never written as plain text to profiles, connection files, command lines, or logs. Leave the password field blank to retain an existing saved password; uncheck the option and save to remove it. Changing the server or username clears the retained password unless you enter a new one. The toolkit removes Credential Manager entries it created when a saved password or site is removed. Encrypted passwords do not transfer to another Windows user or laptop. An entered password can also be used for a single connection without saving it to the profile. Saved sites use a stable, per-site RDP file under the user's data folder; the saved file no longer carries a password blob. Windows display and resource preferences written to that file are retained across launches. Temporary connections and one-off passwords use disposable files removed when the launched Remote Desktop process exits; a crash may leave an encrypted file. Saved connection files are removed when the site is deleted. Windows/server policy may still prompt for credentials. For a site-local account, enter the remote PC name in **Domain** and the account name in **Username**. Keep the IP by itself in **Server / IP**. Certificate trust choices are managed by Windows Remote Desktop; certificate changes and organizational policies can still require another prompt. The toolkit keeps server authentication enabled.

If Windows asks for the password again after you click **Connect** to an IP-based site with a local account, enter the remote PC name in **Domain**, keep the IP alone in **Server / IP**, then click **Save Site** and reconnect. The RDP tab shows this hint after opening a connection. **Password Help** shows the same guidance with a diagnostic report, including whether a toolkit-owned Credential Manager entry matches the saved account and password, without displaying either password value. The toolkit cannot read a password prompt shown inside Windows Remote Desktop, so it does not claim to detect one automatically.

## IP history and site workspace preview

The Sites workspace is hidden in this field-launch release. Existing site data remains in each user's local configuration so it can be shown again in a later release without re-entry. The normal Windows Troubleshooting, IP Shifter, IP Scanner, RDP, Network Troubleshooting, BMS Tools, and Feedback tabs remain visible.

The **IP History** button in IP Shifter shows the last 100 local static IP, DHCP, and restore attempts with their before/after address summaries and verification outcomes. History is saved for the current Windows user; it does not change network settings.

## Feedback

The Feedback tab displays `IT@tec-system.com`. Technicians can copy the address or open a pre-addressed Outlook Web draft in their browser. The technician writes and sends the email there. The toolkit does not send email or handle attachments. Existing screenshot files from older versions are left untouched.

For reliable unattended sending across mixed Outlook versions, TEC Systems IT would need to provide an authenticated company mail service or Microsoft Graph integration. No credentials are stored in this toolkit.

## Verification

The build also checks RDP profile persistence, folder grouping, resolution generation, password encryption/removal, second-process window activation, single-click tray restore, dark/light RDP tree colors, and the update indicator. The build runs `TEC-Systems-FieldToolkit.exe /self-test` to check native startup, visible tabs, tray close/restore/exit, and the absence of a PowerShell assembly reference. The setup also runs `/verify` against its embedded payload. Neither check sends feedback or changes adapter settings. `tests/Smoke-Toolkit.ps1` tests only the legacy script.
